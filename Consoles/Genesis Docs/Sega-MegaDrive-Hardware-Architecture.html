Sega Mega Drive / Genesis — Hardware Architecture

A tour of the real 1988 console hardware: the two-CPU bus structure, the memory map both processors see, how the sound CPU is handed the bus, how the VDP is wired and timed, and where the well-documented facts stop and the reasonable approximations begin.

1 Overview

The Mega Drive (Genesis in North America) is built around two CPUs that never run in true parallel access to the same bus — a fast 16/32-bit main processor and a slower 8-bit sound processor that is handed exclusive control of its own small world and, separately, a keyhole back into the main processor's address space.

  • Motorola 68000 — main CPU. 24-bit address bus, 16-bit data bus, runs the game logic, drives the VDP, and owns the entire memory map by default.
  • Zilog Z80 — sound CPU. 16-bit address bus, 8-bit data bus, normally runs the sound driver independently; the 68000 can pause it and borrow its bus at will.
  • VDP (Video Display Processor) — a custom Yamaha/Sega chip that owns its own private 64KB of VRAM plus small CRAM (palette) and VSRAM (vertical scroll) stores, and is the only device on the 68000 bus with genuine DMA capability.
  • YM2612 — 6-channel FM sound chip, wired only to the Z80's bus.
  • PSG (SN76489-compatible) — 4-channel square-wave/noise chip, physically packaged inside the VDP but addressed from the Z80 side.

Every fact below was cross-checked (where noted) against real hardware documentation and established open-source emulators while this project's own C# emulator, GenesisSharp, was built and debugged against real ROMs — see §11 for the full source list.

2 System bus & block diagram

There are really two separate buses, each with its own address/data lines, bridged in exactly two controlled places rather than merged into one shared bus.

Diagram 1 — system-level bus map: the 68000 bus (cyan backbone) and the Z80 bus (magenta backbone), with the two arbitrated bridges between them in amber.

Everything on the top backbone is visible to the 68000 directly and always; everything on the bottom backbone belongs to the Z80's private world. The two amber paths are the only ways data crosses between them:

  • 68000 → Z80 space ($A00000–$A0FFFF): the 68000 can address the Z80's RAM, YM2612, bank register and PSG directly through this window, but real hardware only guarantees clean results while the Z80's own bus has been requested away from it — see §5.
  • Z80 → 68000 space: a 32KB window at $8000–$FFFF in the Z80's own address space, whose base address is the 15-bit bank register value shifted up by 15 bits (i.e. in 32KB steps). This lets the sound driver stream music/sample data straight out of ROM or work RAM without needing the 68000's help for every byte.

Cartridge ROM header layout

Right after the 256-byte 68000 exception vector table (§5) that every ROM starts with, cartridge ROM has a second fixed-layout 256-byte block — the header — describing the game to anything that cares to read it. Nothing in this block is ever executed: the 68000 jumps straight to whatever PC the vector table gave it (almost always somewhere past the header, not through it), so the header is purely data, read by development tools, some BIOS/menu screens, and modern flash carts/emulators for auto-detecting region and save-RAM support:

Diagram 3 — the standard 256-byte cartridge ROM header at $100–$1FF, directly following the 68000's own exception vector table.
Confidence note

The identification fields (console name, copyright, titles, serial, checksum, I/O support) and the ROM/RAM address-range fields are extremely well and consistently documented across homebrew guides and real ROM dumps. The tail fields — SRAM support, modem support, and region support — are real and well-attested in shape, but this document is less precise about their exact byte boundaries than it is about everything above them. GenesisSharp's own Cartridge.cs is deliberately minimal — a raw byte array with no header parsing at all — so none of this is independently exercised by the emulator itself; it's presented here purely as real-hardware/ROM-format documentation.

5 Z80 bus arbitration

Because both CPUs technically share the Z80's RAM/YM2612/PSG/bank-register region, real hardware needs the 68000 to explicitly ask for — and later release — control of that bus before touching it, and to hold the Z80 in reset while it loads a sound driver into its RAM. This is the standard boot sequence almost every game's startup code performs.

Diagram 4 — the standard boot-time bus-request → hold-reset → load-driver → release-reset → release-bus sequence.

Games also request the bus at runtime (not just at boot) whenever the 68000 needs to write new music/sample data into Z80 RAM mid-game — the same steps 1–3 and 7 without the reset dance, since the driver is already resident. This is why a Z80 bus-request poll (move.w #$100,($A11100); btst #0,($A11101); bne …) is one of the most common idioms you'll see in any real Mega Drive disassembly.

Confidence note

There's a well-documented, subtle undocumented quirk here: the unused bits of a byte/word read from $A11100/$A11101 don't reliably read as zero — they reflect whatever the 68000's own instruction prefetch queue currently holds at its program counter, an open-bus artifact. Code that checks the whole byte/word instead of just bit 0 (Shadow of the Beast is a documented real example) can hang waiting for a value that "should" be clean but isn't. Confirmed against genesis-plus-gx's own comment on this exact behavior.

Z80 bank register window

The bus-request dance above gets the 68000 into the Z80's world. There's a second, completely independent mechanism running the other way: a 32KB window at the top of the Z80's own address space ($8000–$FFFF) that lets the Z80 itself reach out and touch any 32KB page of the 68000's full 16MB address space — ROM, work RAM, even the VDP's ports. This is how a sound driver streams music data straight out of the cartridge instead of needing it all pre-copied into the Z80's tiny 8KB RAM.

Diagram 5 — the Z80's bank register: loaded 1 bit per write (LSB-first), then shifted left 15 to become a 32KB-aligned base address for its own $8000-$FFFF window into the full 68000 address space.
Confidence note

The 9-bit serial-load sequence, the ×$8000 base-address formula, and the 32KB window's transparent pass-through are all consistent with GenesisSharp's own GenesisConsole.cs and match the well-documented real hardware mechanism. The recursion guard (one permitted round-trip, open bus beyond that) is an emulator-side design choice for handling a pathological bank value cleanly — real hardware's actual behavior in that exact situation is bus contention with no clean architectural answer, so this isn't claimed to reproduce a specific documented real-hardware outcome, just to avoid the emulator crashing on an input real hardware would also have handled badly.

TMSS and the full system boot sequence

The Z80 handoff above is one piece of a larger boot sequence every game performs, and — on the later Genesis hardware revisions that have it — TMSS ("TradeMark Security System") sits right at the front of it. TMSS keeps the VDP electrically locked, ignoring register writes, until the 68000 writes the ASCII string "SEGA" ($53454741) to $A14000; Sega added this specifically so unlicensed cartridges would fail to display anything, folding a legal requirement straight into the hardware:

Diagram 6 — the full system boot sequence, TMSS's lock/unlock gate zoomed in below the step it belongs to.
Confidence note

TMSS didn't exist on early Genesis hardware at all — Sega added it partway through the console's production run, originally to help win a legal dispute over unlicensed cartridges — so its exact enforcement varies by hardware revision, and some accounts describe a multi-second warning screen on failure rather than a hard, permanent lock. GenesisSharp's own TMSS register is a plain read/write latch with no gating effect — its VDP always responds regardless of what's written to $A14000 — a deliberate simplification: every real game already performs the "SEGA" write as a matter of course, so enforcing the lock would only risk rejecting a ROM an emulator wants to run, without adding anything a real game's own boot code doesn't already handle.

6 The VDP

The VDP is the most complex chip in the system: it owns its own memory, decodes a two-word command protocol over two 68000-visible ports, can DMA autonomously, and renders the entire display line by line from a completely separate internal pipeline.

Diagram 7 — VDP internal architecture: ports, internal memories, DMA engine and render pipeline.

Registers & ports at a glance

  • 24 registers control display mode (H32/H40, interlace, 224/240-line select), the four name-table base addresses (planes A/B, window, sprites), horizontal scroll table base, background color, auto-increment, plane dimensions, window split position, and the three DMA registers (length, source address, mode).
  • Data port — reads/writes whichever of VRAM/CRAM/VSRAM the last command word selected, at the current auto-incrementing address.
  • Control port — accepts the two-word address/command sequence, plain register writes, and doubles as the status register on read (DMA busy, HBlank, VBlank, sprite overflow/collision, FIFO full/empty, PAL/NTSC, odd-frame flags).
  • HV-counter port — read-only snapshot of the current horizontal and vertical raster position, used by games doing raster-timed effects.

Rendering priority order

For every pixel on every scanline, the VDP has up to six candidate layers to choose from (two priority levels each of sprites, plane A, and plane B) plus a backdrop that's always available as a last resort. It picks between them with a fixed, non-negotiable pecking order — checked top to bottom below; the first layer that actually has an opaque (sprite) or nonzero-color (plane) pixel at that position wins, and every layer under it is simply never drawn there:

Diagram 8 — per-pixel compositing order: sprites and planes each get a high- and low-priority pass, window silently stands in for plane A, and the backdrop never fails to produce a color.

A sprite's own attribute-table priority bit picks which of the two sprite slots (1 or 4) it competes in; the same idea applies to each individual plane-A/plane-B tile's priority bit in its name-table entry — priority is a per-tile/per-sprite decision, not a whole-plane setting.

The window plane

The window is a fourth name table (its own base address, register 3) that silently takes over plane A's slot in the priority stack above, for whichever rows or columns it's configured to cover. Unlike planes A and B, it's never scrolled — its screen coordinates map straight onto its name table with no H/V-scroll math involved at all, which is exactly why games use it for things that must stay pinned to the screen: status bars, HUDs, unmoving borders around a scrolling play-field.

Where it's active is set by two independent splits: register 17 (a horizontal split column, plus a flag for whether the window covers columns left or right of it) and register 18 (a vertical split row, plus a flag for above or below it). Real games overwhelmingly use one dimension at a time:

Diagram 9 — the window plane's two common configurations. Both splits can be active at once — hardware then draws window wherever either condition holds, producing an L-shaped region — but real games essentially always commit to just one dimension, as shown here.
Confidence note

The split-position and left/right/above/below semantics above are confirmed against GenesisSharp's own source and general VDP documentation. The window's internal row-stride constant — 32 cells per row in H32, 64 in H40 — is confirmed against Genesis Plus GX's vdp_ctrl.c register-3 write handler and vdp_render.c's row-address shift: real hardware pre-allocates a fixed 64-cell-wide window row in H40 even though only 40 columns are ever displayed, which is why the base address must be 4KB-aligned in H40 versus 2KB-aligned in H32 (independently corroborated by SGDK's own alignment requirement for the window base register).

Horizontal scroll modes

Register 11's low two bits pick how finely plane A/B's horizontal scroll can vary down the screen, by selecting how many bits of the current line number are used to index into the H-scroll table in VRAM:

Diagram 10 — the three meaningful horizontal-scroll granularities, shown as what happens to what would otherwise be one straight vertical edge in the tile pattern. (Code 01 is a degenerate/reserved combination, not a fourth real mode.)

This is consistent with genesis-plus-gx's own H-scroll decode logic, which selects the table index via a mask applied to the current line number — a mask of all-zero bits collapses every line to table entry 0 (full-screen), a mask covering the line number down to its lowest 3 bits cleared groups every 8 lines together (per-row), and an all-ones mask lets every line differ (per-line).

Vertical scroll modes

Register 11 bit 2 picks between just two vertical-scroll granularities — coarser than the horizontal options above, because VSRAM only holds 40 words total (80 bytes), nowhere near enough for a value per scanline:

Diagram 11 — vertical scroll's two modes, shown as what happens to what would otherwise be one straight horizontal line. Per-2-column indexes VSRAM as (x>>4)×2 + plane — 20 column-pairs × 2 planes exactly fills VSRAM's 40 words.

Sprite multi-cell layout and flip

A sprite spanning more than one 8×8 cell stores its tiles in VRAM column-major — every row of the first column, then every row of the second column, and so on — which is the opposite of the row-major order the plane name tables use. Flipping such a sprite mirrors the whole multi-cell shape as one unit: the tile order reverses across columns (or rows, for a vertical flip) at the same time each individual tile's own pixels mirror, so a flipped multi-cell sprite still reassembles correctly instead of just mirroring each cell in place:

Diagram 12 — column-major sprite storage (left) and what horizontal flip actually does to it (right): the column order reverses, not just each tile's pixels — the whole shape flips as one unit.

The sprite-masking quirk

Sprites aren't evaluated in attribute-table order, and they aren't evaluated in screen-position order either — each scanline, the VDP walks a linked list starting at sprite 0, where each sprite's own Link field names the next sprite to check. That order is whatever the game last set it to, completely independent of where any sprite actually sits on screen. Real hardware has a specific, documented failure mode buried in that traversal: if a sprite with a raw X coordinate of exactly 0 shows up in that link order and it is not the very first sprite checked on the line, the VDP stops evaluating the list immediately — every sprite still to come in link order is simply never drawn on that line at all, regardless of where on screen it was actually supposed to appear:

Diagram 13 — the sprite-masking quirk: a non-first sprite with raw X=0 halts the whole per-line link-list traversal, silently dropping every sprite still to come in that order.

Collision/overflow bookkeeping happens independently of both the priority stack above and this masking rule: the first sprite actually drawn to a given pixel (again in link-list order, not priority order) is the one credited if a later sprite also tries to draw there.

Shadow/highlight mode

Worth being upfront about here: shadow/highlight isn't a scanline-level timing mechanism the way HINT, DMA, or interlace are. There's no counter, no multi-line carry-over, nothing that spans more than a single pixel's decision. It's a per-pixel color rule bolted directly onto the same priority stack from earlier in this section, evaluated exactly once per pixel in the same pass that decides which layer wins that pixel in the first place. The diagram below shows it exactly that way — as one more row added underneath the per-pixel decision, swept across a line — rather than pretending it has timing behavior of its own.

When enabled (register 12 bit 3), every pixel gets a default brightness purely from which priority level won it in Diagram 8's stack: pixels won by a low-priority layer (or the backdrop) default to shadow (half brightness); pixels won by a high-priority layer default to normal. That default can then be overridden, regardless of which priority level actually won: a sprite drawn with palette line 3, color index 14 (the "highlight operator") or color 15 (the "shadow operator") never appears as a visible color itself — instead, wherever it's the topmost sprite at a pixel, it forces that pixel to highlight or shadow, overriding whatever the priority-based default would have been. (An earlier version of this document had these two colors swapped — 14 and 15 are shown correctly matched to Diagram 14 below.)

A separate, distinct quirk applies outside palette line 3: a sprite drawn with color index 14 on palette line 0, 1, or 2 is not an operator at all — it draws its own color normally — but is unconditionally exempt from the default shadow rule above, regardless of its own priority bit. In effect, that one color index is permanently "pinned" to normal brightness on those three palette lines, while remaining a completely ordinary, fully-opaque sprite color everywhere else.

Diagram 14 — shadow/highlight as a per-pixel color rule layered on the priority stack: a default from which layer wins, optionally overridden by an operator sprite, with no scanline-spanning timing of its own.
Confidence note

The priority-based default (low priority → shadow, high priority → normal), the color-15 shadow operator, and the color-14/palette-0-2 normal-brightness pin are all confirmed against Genesis Plus GX's vdp_render.c (palette_init() and make_lut_bgobj_ste()). The real VDP DAC turns out to be a discrete 3-bit-per-channel model rather than a continuous blend: shadow reads each CRAM channel's raw 3-bit value directly (0-7), normal doubles it (0-14, even values only), and highlight adds 7 (7-14) — the "half brightness" / "partway to white" framing above is really just a plain- language description of that same discrete math, not a separate looser approximation.

One piece is deliberately left unresolved: the color-14 highlight operator's exact behavior in Genesis Plus GX's source branches on an incoming background intensity state produced by an earlier compositing stage that wasn't traced all the way back. Both literal readings of that branch suggest the common case might actually resolve to normal brightness rather than highlight — which would contradict this document's own framing above, itself drawn from long-standing, widely-cited community documentation (e.g. Charles MacDonald's genvdp.txt). Rather than silently flip a widely-cited behavior on an unverified re-derivation, GenesisSharp keeps the conventional "always highlight" behavior and flags the conflict for whoever traces that earlier stage next. Edge cases like a pixel simultaneously overlapped by both operators from different sources are also not independently re-confirmed here.

Mode 4 rendering

Everything covered so far in this section is Mode 5 — the Genesis's own native mode, and the one essentially every commercial game uses. Register 1 bit 2 can instead select Mode 4: a backward-compatibility mode inherited from the Sega Master System's TMS9918-derived VDP, present mainly so SMS software (and VDP test suites) can run on the same chip. It isn't a smaller version of Mode 5 — it's a genuinely different tile format, a genuinely different sprite table layout, and a smaller, fixed display area:

Confidence note

Mode 4 is essentially unused by real Genesis software — it exists for Master System backward-compatibility and VDP test ROMs, not anything a commercial Genesis game shipped with. The structural facts above (tile/sprite-table format, fixed display size, backdrop-from-sprite-palette quirk, the Y+1 sprite offset, the sentinel, the 8-sprite-per-line cap) are confirmed against Genesis Plus GX's own Mode 4 renderer, including confirming that a tile-index-masking quirk specific to the real standalone SMS chip (315-5124) is correctly absent from Genesis Mode 4 compatibility — the reference source itself gates that quirk off for anything above plain SMS hardware.

Two things that comparison surfaced but didn't resolve, worth flagging rather than glossing over: Genesis Plus GX applies a separate, register-6-based sprite pattern-index mask that does apply to Genesis-class hardware and isn't reproduced here at all, and there's a possible mismatch between this document's assumption that Mode 4 background tiles support horizontal/vertical flip and Genesis Plus GX's tile-index bit width for the same field. Given how little real software depends on Mode 4 correctness at all, neither was chased down further — they're the first place to look if this mode's confidence ever needs raising past "structurally verified, two specific details still open."

7 Frame & scanline timing

This is the section to read slowly if raster timing has never quite clicked before — the whole system rests on one simple idea (two nested counters) applied very literally. Once that idea is clear, everything else in this section — why interrupts fire when they do, why DMA has to compete for VRAM access, why some effects only work mid-scanline — falls out of it directly.

The big picture: two nested counters

A CRT television doesn't have pixels sitting in memory the way a modern display does — it has an electron beam that physically sweeps left-to-right across the screen, then jumps back to the left edge one line lower, over and over, top to bottom, then jumps back to the top-left corner to start the next frame. The VDP's entire job is to figure out, at every instant, "what color should the beam be drawing right now?" — and it answers that question with exactly two counters:

  • The H-counter — tracks the beam's horizontal position within the current line. It resets to 0 at the start of every line and counts up once per pixel clock tick (§3) until the line ends, then resets again.
  • The V-counter — tracks which line the beam is currently on, within the current frame. It increments once per line (right as the H-counter resets) and resets back to 0 once per frame.

Everything else — the HBlank flag, the VBlank flag, the HINT and VINT interrupts, the exact moment VRAM becomes easy or hard for the CPU to reach — is just a simple comparison against one or both of these two numbers. "Are we in HBlank?" means "is the H-counter past the active display's width?" "Are we in VBlank?" means "is the V-counter past the active display's height?" There's no other hidden state driving display timing beyond these two counters and a handful of fixed thresholds.

Frame structure (vertical)

Diagram 16 — one video frame, NTSC vs. PAL. Same active-display height, different vertical-blank length (which is what changes the refresh rate).

To state the numbers plainly, since the diagram above only has room to abbreviate them: the Mega Drive always outputs a fixed number of scanlines per frame — fixed by the video timing standard the console was built for, not by anything any individual game does. That total is 262 lines/frame for NTSC (60 Hz regions — North America, Japan) and 313 lines/frame for PAL (50 Hz regions — Europe, Australia). Whichever total applies, only some of those lines are active (visible); the rest are vertical blank — and exactly how many fall on each side depends on whether the game selects 224-line or 240-line active mode (register 1 bit 3, "V30"):

Every row above is just "total minus active" — vertical blank isn't a separately-specified quantity anywhere in the hardware, it's simply whatever's left over once the active region ends and the fixed per-region total is reached. PAL's extra 51 lines over NTSC (313 − 262) all land in vertical blank, which is the entire reason PAL Genesis games run at a visibly lower frame rate (≈49.7 Hz vs. ≈59.92 Hz) despite drawing the exact same 224 (or 240) lines of picture — the picture itself never changes size, only how long the console dwells in the invisible part of the frame around it.

One frame, step by step

Concretely, in NTSC/H40 — the combination almost every commercial game uses — here's what the V-counter actually does over the course of one 1/59.92-second frame:

  1. V-counter = 0. The beam is at the top-left corner. This is also the exact instant the H-interrupt countdown (see below) and every plane's rendering for this line begin.
  2. V-counter = 0 through 223 (224 lines) — active display. Each of these lines is rendered for real: the VDP walks the render-priority stack from §6 for every one of the line's 320 (H40) or 256 (H32) pixels. During these lines the CPU/DMA access-slot budget is at its smallest (§8) — the VDP itself is busy reading VRAM to build the picture, so there's little spare bandwidth left over for the 68000 to also poke at VRAM without stalling.
  3. V-counter = 224 — vertical blank begins. The VBlank status flag goes high and stays high for the rest of the frame; this is also the exact line on which VINT fires (68000 IPL 6 and the Z80's maskable INT, simultaneously — §9). Essentially every game's main loop is structured around waiting for this one moment.
  4. V-counter = 224 through 261 (NTSC) / 312 (PAL) — vertical blank. The beam is still sweeping (there's no way to stop it — the counters keep running unconditionally), but nothing it "draws" during this period is actually visible on screen. This is the window where access-slot budgets are largest (§8), so it's the conventional place to run large VRAM DMA transfers — tile/palette uploads for the next frame, typically.
  5. V-counter wraps back to 0. The cycle repeats, 59.92 times a second (NTSC) or 49.7 times a second (PAL).

The numbers behind that repetition rate are worth spelling out, because they tie directly back to the clock tree in §3: one scanline lasts exactly 3420 master-clock cycles, which — divided by the 68000's own ÷7 clock — comes out to about 488 68000 cycles per line. Multiply by 262 lines and one whole NTSC frame is 3420 × 262 = 895,640 master-clock cycles, or 488 × 262 ≈ 127,880 68000 cycles — at ≈7.67 MHz, that's ≈16.67 milliseconds, i.e. 1/59.92 second. (GenesisSharp's own scanline loop uses a 488-cycle-per-line 68000 budget for exactly this reason — real hardware's per-line cycle count, not an arbitrary round number.) Every raster-timed effect a game performs — parallax split points, palette swaps mid-screen, the classic "wobble" tricks — works by racing the 68000 against this same 488-cycles-per-line budget, one line at a time.

The frame loop, visualized

Pulling the last several pages into one picture: everything this document has covered scanline-by-scanline is really happening at once, every line, because every subsystem shares the same master clock. Real silicon doesn't run a "loop" the way software does — but the causal order below (what has to be true before what) is real, and it's exactly the order any accurate software implementation (this emulator included) has to reproduce to stay in sync:

V-counter's non-linear jump

This is worth being precise about, because it's easy to accidentally wire the wrong two things together. The VDP has its own internal line sequencer that just counts every real scanline, 0 through 261 (NTSC), with zero ambiguity — that internal count is what flips the VBlank flag at line 224 and holds it flipped for all 38 remaining lines of the frame (224 through 261, inclusive), and it's what every rendering, interrupt, and access-slot decision in this document actually runs on. Nothing about that internal count ever jumps, skips, or repeats — it's as boring and linear as a counter can be.

The V-counter register discussed below is a separate, secondary thing: a read-only 8-bit snapshot of that internal count, exposed through the HV-counter port (§6) purely so software can poll it for raster-timing tricks. An 8-bit byte can only hold 256 distinct values, but NTSC has 262 real lines to report — 6 more than a byte can distinguish — so this exposed snapshot alone has to reuse a few codes partway through vertical blank. That reuse is what the jump below is showing. It is only a quirk of the number software gets to read back; it doesn't cause, extend, or shorten any blanking, and it isn't the reason anything fails to draw.

Concretely, to answer the "why don't the last 27 lines draw" question directly: they aren't special. All 38 lines of vertical blank fail to draw — lines 224 through 261 — for the same one reason given in §7's opening paragraphs (the VBlank flag is high, so nothing rendered during this span is visible). The jump illustrated below happens at line 234, which is ten lines after blanking already began at line 224. The "27" is merely how many byte-codes are left between the jump and the end of the register's range (0xE5–0xFF) — it describes the back half of the register's own numbering scheme, not a second, separate blanking period. The first ten blanked lines (224–233) are already fully blanked while the register is still counting up normally, before its internal jump has even happened.

Diagram 18 — the VBlank flag (amber shading, from line 224) and the V-counter register's internal jump (line 234) are two unrelated events; blanking starts well before the register ever jumps.

The arithmetic behind the jump itself is still worth working through once, because it explains exactly why the register has to do this rather than leaving it as an arbitrary quirk to memorize. It counts up normally from 0x00 to 0xEA (235 values, covering lines 0–234), then jumps back down to 0xE5 and counts up a second time through to 0xFF (27 more values, covering lines 235–261). 235 + 27 = 262 — every real line gets a representable code, at the cost of the six codes 0xE5–0xEA each being reused for two different real lines. A raster-timing routine that reads the register and sees, say, 0xE7 genuinely cannot tell from that byte alone whether it's on the line ~231 or the line ~240 — real hardware has that exact ambiguity built in, it isn't an emulation shortcut. It's an ambiguity in the readable label only, though — the VDP itself, internally, never confuses the two lines for a moment.

H-interrupt timing

HINT is driven by a small down-counter, completely separate from the H-counter and V-counter discussed above, that only ever ticks once per active line — never during HBlank, never during vertical blank. It reloads from register 10 every time it fires, which is exactly why the interrupt recurs every (register 10) + 1 active lines: the "+1" accounts for the line on which the counter actually reaches zero and fires, not just the lines spent counting down to it.

Diagram 20 — H-interrupt timing: a down-counter that decrements once per active line, fires and reloads on underflow, and sits frozen (never firing) for the entire vertical-blank period.

This is also why HINT is useless for anything tied to vertical position during blanking — since the counter is held reloaded rather than counting through those lines, there's no way for a game to use it to "count into" vertical blank the way it can count through active lines. Raster effects built on HINT (split-screen parallax, per-line palette swaps, the classic copper-style tricks) are therefore inherently an active-display-only technique; anything timed against vertical blank instead uses VINT (§9), which fires exactly once, right as blanking begins.

What's actually happening, moment to moment

Zooming into a single scanline: the H-counter's value at any instant is directly what decides which of three things is true right now. Lining up the H-counter's value, the HBlank flag it controls, and the CPU/DMA access-slot budget from §8 against each other makes the cause-and-effect chain explicit:

Diagram 21 — the same scanline shown three ways at once: the H-counter's raw value, the HBlank flag it drives, and the CPU/DMA access-slot budget that flag effectively controls (H40 figures from §8).

The three rows above are really one causal chain, not three independent facts: the H-counter's value is compared against the active-display width; once it's past that width, HBlank goes high; and HBlank being high is what lets the VDP hand the vast majority of its access slots over to the CPU and any in-progress DMA instead of reserving them for its own rendering. It's the same underlying mechanism at the frame level too (VBlank vs. active display, §8's per-line slot table just has bigger numbers during it) — a scanline is really a small, fast-forward copy of the same active/blanking split a whole frame has.

Putting it all together: a game's main loop is, at its core, built around this one nested structure. It does its heavy VRAM/CRAM work either during vertical blank (204 vs. 18 access slots per line in H40 — over 11× the headroom, §8) or — for effects that must change mid-screen — timed against the H-interrupt firing every (register 10) + 1 lines (§9), racing the ~488-cycle 68000 budget each of those lines gives it before the next one starts. Every number in this section — 262 lines, 488 cycles/line, 320 or 256 active pixels, 18 or 204 access slots — is a fixed fact about the hardware that every real game's timing is built directly on top of.

Confidence note

The 342/420 H-counter-tick figures per line, and the 3420-master-clock-cycles-per-line figure they derive from, are widely cited (Charles MacDonald's genvdp.txt, Plutiedev's VDP timing notes) and are consistent with the documented ≈59.92 Hz NTSC frame rate (53,693,175 Hz ÷ 3420 cycles/line ÷ 262 lines ≈ 59.92 Hz). The H-counter's non-linear jump — like the V-counter's — is now confirmed against Genesis Plus GX's per-master-cycle cycle2hc32/cycle2hc40 lookup tables: H32 counts 0x00- 0x93 then jumps straight to 0xE9-0xFF; H40 counts 0x00-0xB6 then jumps to 0xE4-0xFF. What is not independently re-verified — and is flagged the same way in GenesisSharp's own source — is the exact dot-for-dot repeat pattern within a line: Genesis Plus GX's own tables show H40's real pixel clock alternating between two different rates (an EDCLK quirk), which isn't reproduced bit-for-bit here; what's confirmed is the correct visible-value set and the jump's location, spread proportionally across the line rather than clocked cycle-by-cycle.

Interlace mode timing

Interlace (register 12, bits 4–5) doesn't change any of the numbers established above — same 262 (NTSC) or 313 (PAL) lines, same 488-cycle-per-line 68000 budget, same VBlank/HINT behavior. What it changes is what a "line" means: every frame the VDP renders is now one of two alternating fields, and a status-register bit (the "odd-frame" flag mentioned in §6) flips between 0 and 1 every single field so software — and a real interlace-capable display — can tell which one is currently being drawn.

Diagram 22 — interlace mode: two fields, each running the ordinary 262-line NTSC timing at the ordinary rate, whose lines land at vertically offset positions so a real interlaced display can combine them into one higher-resolution picture.

That half-line vertical offset is IM1 (register 12 = 01) — a positional trick only, where both fields keep reading the exact same VRAM tile data and just display it shifted, which is why it's of little use to a game that wants each field to actually show something different. IM2 (register 12 = 11) goes further, and the actual addressing scheme is more intricate than "double the tile index": a name-table entry's pattern index drops its top bit and instead selects a pair of adjacent real VRAM tiles — treat them as the top and bottom half of one logical 16-row-tall tile. Within whichever half a given row falls in, each field doesn't read that physical tile's rows in order; it samples every other row, offset by which field is currently being drawn. That's what actually produces the doubled-vertical-detail effect once both fields are combined — this is the mode Sonic 2's two-player split-screen uses to get a taller combined picture out of two distinct fields. Either way, the field rate is unchanged: a game gains vertical detail by combining two fields, not by rendering any faster.

Confidence note

Interlace sees essentially no real-world use beyond the one commonly-cited Sonic 2 example, and displaying it correctly requires an actual interlace-capable display or a deinterlacing step — neither of which most emulators (or modern LCDs) bother with, so it's one of the least real-world-exercised corners of the whole VDP. Unlike every other area touched in GenesisSharp's recent VDP accuracy pass, this one has no real ROM and no known- correct reference output to check against. The paired-tile addressing description above was hand-derived from Genesis Plus GX's tile-cache address arithmetic rather than read off an explanatory comment, and while working through it did catch a genuine, fixable bug (the previous formula doubled the *full* pattern-index range instead of masking off its top bit first, corrupting addressing for higher tile indices), the overall scheme is explicitly labeled a best-effort reconstruction in GenesisSharp's own source, not a confirmed fact — it is, honestly, the single least-verified claim anywhere in this document.

8 DMA & VRAM access slots

The VDP doesn't get free, instantaneous access to VRAM whenever it wants — each scanline it's allotted a fixed number of "access slots," and every VRAM read or write (whether from the CPU or from a DMA in progress) consumes one. Run out of slots and the transfer simply continues on the next line.

ModeSlots/line — active displaySlots/line — blanking
H32 (256px)16166
H40 (320px)18204

This is why large DMA transfers are conventionally done during vertical blank (far more slots per line are available) rather than mid-frame. The three DMA modes cost differently per unit transferred:

  • 68000-memory-to-VRAM — 1 slot per byte.
  • VRAM fill — 1 slot per byte (the fill value itself arrives via the very next data-port write after the command).
  • VRAM-to-VRAM copy — 2 slots per byte (one read + one write) — a detail easy to under-count if you only think of it as "one transfer."

A dedicated status-register bit reports "DMA busy," which homebrew SDKs (SGDK's VDP_waitDMACompletion among them) poll directly rather than counting cycles themselves.

DMA timing relative to scanlines

A DMA transfer doesn't run to completion in one uninterrupted burst — it's metered by the exact same per-line access-slot budget as everything else in §7, one line at a time. If a transfer is bigger than what fits in a single line's slot allowance, it simply carries the remainder over to the next line, and the next, for as many lines as it takes — which means where in the frame a DMA starts has a direct, calculable effect on how long it actually takes to finish.

Concretely: take a 256-tile (8192-byte) graphics upload, triggered via 68000-memory-to-VRAM DMA (1 slot/byte) right at the instant vertical blank begins, in H40. Vertical blank gives it 204 slots/line for 38 lines — 38 × 204 = 7752 slots — which isn't quite enough: 8192 − 7752 = 440 bytes are still left when active display resumes. Those last 440 bytes now have to compete for only 18 slots/line, needing ⌈440 ÷ 18⌉ = 25 more lines to finish — so this single transfer, despite being conventionally "done during vblank," actually keeps running for the first 25 lines of visible picture in the next frame, at roughly 1/11th the speed it was running at a moment before:

Diagram 24 — an 8192-byte DMA triggered at the start of vertical blank: the steep drop shows vblank's generous 204-slot/line rate; the shallow tail shows the same transfer finishing at active display's much stingier 18-slot/line rate.

The lesson generalizes directly: vblank's slot budget is generous but not infinite, and any transfer sized against "however long vblank happens to be" without checking the arithmetic will silently spill into visible scanlines, competing with the VDP's own rendering for the same limited slots for however many lines it takes to drain the remainder. This is exactly the kind of budget SGDK-style DMA-completion polling (mentioned above) is meant to guard against — a game can check whether a transfer is still running before assuming it's safe to reuse that VRAM region, rather than assuming vblank was always going to be long enough.

The 68000's priority encoder only ever presents its single highest currently-asserted interrupt level — VBlank (6) always wins over a simultaneously-pending H-interrupt (4). The Z80's side is much simpler: one maskable INT line, gated entirely by its own interrupt-enable flip-flop, plus an NMI line that exists on the chip but isn't wired to anything on this console.

10 Audio subsystem

Two independent sound generators, both only reachable from the Z80 side of the bus, mixed together in the analog domain on real hardware (and in software, post-generation, by an emulator).

YM2612 — FM synthesis

  • 6 channels, 4 operators each, 8 selectable algorithms (operator routing graphs).
  • Channel 6 can be switched from FM to raw 8-bit PCM playback (the DAC path) — the mechanism most games use for sampled drums/voice clips.
  • Two independent timers (A and B), meant to be polled via the status register for driver timing, not wired to any interrupt.
  • Documented real power-on quirk: the pan registers default to both L+R enabled rather than silent — several real games (including Sonic 1's own "SEGA" voice sample) rely on this instead of setting pan explicitly.

PSG — square wave / noise

  • SN76489-compatible: 3 tone channels + 1 noise channel, 4-bit attenuation per channel (2 dB/step, level 15 = silence).
  • Write-only register-latch protocol — bit 7 selects which register a following byte targets.
  • The noise channel's 16-bit LFSR feeds back into bit 15 on the Sega-integrated variant used here (a detail that differs from some generic discrete SN76489 implementations).
  • Documented real power-on quirk: volume registers default to maximum attenuation (silence), not zero — the opposite of what a naive "clear everything" reset would do.

Both chips are clocked from the tree in §3 (YM2612 from the same signal as the 68000, PSG from the same signal as the Z80), so their pitch accuracy is ultimately tied to the same master crystal as everything else in the system.

Audio timing

The one genuine scanline-relative timing mechanism either sound chip has is the YM2612's pair of free-running timers — and the most important thing to understand about them is what they don't do: unlike HINT (§7), they are never gated by blanking. The sound chip has no concept of a video frame at all, so both timers just keep counting straight through vertical blank, exactly as they do during active display:

Diagram 25 — audio timing: YM2612's Timer A/B run continuously (no vblank gating, unlike HINT), while the 44.1 kHz figure below is purely a digitization choice for modern playback, not something real hardware has any concept of.

Real Genesis hardware has no "sample rate" anywhere in it — the YM2612 and PSG produce continuous analog output, mixed by simple analog circuitry and sent straight to the audio jack/RF modulator. 44,100 Hz only enters the picture because a modern digital pipeline (this emulator included) has to slice that continuous signal into discrete samples somewhere; picking that number is an emulator/playback decision, not a hardware fact being modeled.

Channel 6 DAC/PCM playback

Alongside its 6 FM channels, the YM2612 has one more trick that most Genesis games actually lean on for drum hits and voice samples: channel 6 can be switched from FM synthesis to raw 8-bit PCM playback. It's a real, well-documented part of the chip — but the mechanism is far simpler than a modern sampler, and understanding exactly how simple it is explains some otherwise-odd-looking driver code.

Diagram 26 — channel 6's DAC/PCM path: register 0x2B's bit 7 picks the channel's one output source, and while DAC mode is selected, 0x2A is just a plain sample-and-hold latch a driver keeps rewriting.
Confidence note

Registers 0x2A/0x2B, the sample-and-hold (no FIFO) behavior, and DAC mode's total replacement of channel 6's FM output are well-documented YM2612 facts, consistent with GenesisSharp's own Ym2612.cs. Pacing 0x2A writes off Timer A overflow (as Sonic 1's own "SEGA" voice sample does) is a common real driver technique worth knowing about, but it's a software convention riding on top of the hardware, not something the DAC register itself requires or enforces — a driver is free to write 0x2A on any schedule it likes, including irregularly.

PSG register-latch protocol

The PSG's entire register file is written through a single byte stream — there's no address port separate from the data port the way the VDP or YM2612 have. Bit 7 of every byte written tells the chip which of two things that byte is:

Diagram 27 — the PSG's register-latch protocol: one write-only byte stream, told apart by bit 7, feeding 8 registers that are each either one byte (volume/noise-control) or two (tone frequency).
Confidence note

The latch/data byte format, the 8-register map, and the two-write tone-frequency sequence match both the well-documented SN76489 protocol and GenesisSharp's own Psg.cs. The dual-bus write path (Z80 at 0x7F11, 68000 directly at 0xC00011, no arbitration needed) is also accurate for Genesis specifically — it's a documented consequence of how the PSG is wired on this particular board, not a general SN76489 fact true of every system using the chip.

11 Controller ports

Both controller ports (plus a third, rarely-used EXT port) are simple 9-pin connectors wired into the same I/O register block as the version register (§4) — but the connector only carries a handful of data lines for what needs to report 8 buttons per pad (and, for a 6-button pad, 12). The console gets there by multiplexing: it drives one output line and reads back a different meaning off the same 6 input lines depending on what it just drove.

3-button (TH-multiplexed) protocol

The console drives a single output line, TH, and reads 6 input lines (D0–D5) back. Which physical buttons those 6 lines represent flips depending on whether TH is currently high or low — so a full read of all 8 buttons on a standard pad takes two reads, one at each TH level:

Diagram 28 — the 3-button protocol's two TH states. The same 6 physical lines report completely different buttons depending on what the console just drove.

6-button extended detection sequence

A 6-button pad (with X, Y, Z, and Mode) can't just add four more physical lines — the connector doesn't have them. Instead it hides behind the exact same 6 lines, distinguishing itself only by how it responds to a specific rapid TH toggle sequence that a normal 3-button poll routine would never perform:

Diagram 29 — the 6-button extended-data sequence: the third TH=0 read forces all four of D0-3 low (not just D2-3) as the "tell," and the very next TH=1 read presents X/Y/Z/Mode where the D-pad would normally be.
Confidence note

The step sequence itself — TH toggled seven times, the third low read forcing all four data bits low, the following high read presenting the extra four buttons — is solidly and consistently documented and matches GenesisSharp's own source. The exact timeout duration (~1.5ms) is the one detail flagged in that same source as only moderately confident; the sequence's existence and shape are far better established than that specific number.

Version register

The same I/O block includes a read-only version register at $A10000, letting software detect region and video standard without guessing:

Bits 7 and 6 (region and video standard) are the two widely and consistently documented ones. The remaining bits' exact meaning is not independently re-verified in this document — GenesisSharp's own version register is a plain fixed-default latch ($A0) rather than a fully decoded model of every bit.
